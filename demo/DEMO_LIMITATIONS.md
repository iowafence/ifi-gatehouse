# DEMO_LIMITATIONS — accurate technical disclosure

**What the demo demonstrates:** evidence verification and controlled human adoption of AI suggestions — AI interprets (stored AMD outputs), code verifies and calculates, humans authorize.
**What it does not demonstrate:**
1. **No live AMD inference.** Everything in AI Findings is a previously recorded response replayed offline (`LIVE_CALLS_DISABLED` in force). Spatial Test 003 itself was a separate, authorized live run earlier; its results are stored, frozen and hash-verified.
2. **Real spatial understanding is NOT demonstrated.** Two completed spatial attempts (one model, one sheet): gate-label localization scored 7/7 checks; gate-symbol relationships verified: 0; fence-type leader targets: 1 confirmed (A), 1 contradicted twice (B, model said “clear”); a keynote was reported as a type tag (false candidate); Spatial Test 003’s predefined success criterion was NOT MET. Two crops clip or omit the gate symbol they were asked about.
3. **Not all 32 real findings are verified.** 14 of them come from a different 34×22 drawing file (12 text facts verified on that file; only 1 also appears on the ANSI B sheet) and cannot be accepted into DP-001.
4. **No simulated findings ship.** The ledger holds only stored real model outputs. Guard tests build their own simulated fixtures inside the test files.
5. **DP-001 is not bid-ready.** Gate G3’s opening, post size and footing are unresolved RFIs (never defaulted); post counts rest on provisional geometry (human reading of C101); the quantity ruleset is an unapproved draft; one flat drilling rate and one concrete rate. The engine itself classifies every priceable state `bid_ready: false`.
6. **The two reference totals are conditional.** They reproduce only under the self-declared G3 what-if (12 ft · 2.875 in · 16×48 in) **and** the reference crew plan (CR13 preferred, CR13 drilling); other crew choices price differently (shown in the crew comparison). They come from the engine; the harness compares them with the accepted reference and does not inject them.
7. **Identity and persistence.** Names are self-declared and unauthenticated; decisions are not durable production approvals. Web-session state (takeoff-review attestations, AI decision marks, the engine’s `artifact_kind` from the release response) is kept in web-server memory; engine projects are in engine memory and expire after 6 h idle (browser sessions after 12 h) — re-stage if staged more than ~5 h before presenting.
8. **Restart behaviour (verified):** after a web-server restart a *released* project no longer shows `artifact_kind` — the banner then reads “issued by the engine only when a release is recorded” although the project is released (`bid_ready` and `release_class` still show, both server-derived). An *unreleased* staged project loses its takeoff-review attestation, so Release is disabled (fail-closed) until the review is re-recorded (≈20 s, tested). An engine restart removes all projects; sessions then restart fresh. Workaround: do not restart services between staging and presenting; re-stage instead. Nothing is fabricated on recovery.
9. **Rate limits.** The proxy allows 12 new demo projects per hour per IP (in memory). Staging uses 3; each judge reset uses 1.
10. **Plan-north assumption.** Mapping the AI’s top/left/right to N/W/E assumes plan north is up (flagged in the ledger).
11. **Harness overlays** (scene captions, the red “actual API response” box) are added by the recording script only; the app itself shows none.
