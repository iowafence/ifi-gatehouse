# Gatehouse HTTP adapter contract `gatehouse-http-adapter.v1-proposed`

**Status: PROPOSED. NOT APPROVED.** It cannot be marked APPROVED until the engine and web owners resolve the open decisions in section 15. It is versioned independently of `pricing-service.v1` (frozen; unchanged by this document). Describes the isolated pass-2 copy; tests named below are in `tests/`.

## 1. Scope and layering
Browser -> (server-side proxy, holds `X-Engine-Key`) -> **this adapter** (`api/server.py`, `engine/integration.py`) -> `engine/pricing_service.py` (frozen `pricing-service.v1`) and `engine/workflow.py` (gate decisions) -> `pricing/*` (deterministic engine). The browser never computes money, hours or digests.

## 2. Routes, schemas and stable error codes
Every error body is `{error, code, ...}`; `code` is stable, `error` is human text. All bodies are JSON objects; unknown fields -> 400 `BAD_REQUEST`. Decision bodies need non-blank `by` and `note` (self-declared, see section 9).

| Route | Request | Success | Notes |
|---|---|---|---|
| POST `/demo/projects` | ignored | 201 summary | creates an isolated fictional project; needs `X-Demo-Owner` |
| GET `/projects/{id}` | none | 200 summary | summary = engine state view + `pricing` + `adapter` |
| POST `/projects/{id}/scope/resolve` | `{exception_id, option_id\|value, by, note}` | 200 summary | engine `workflow.resolve` |
| POST `/projects/{id}/decisions/ruleset-approval` | `{by, note, ruleset_sha256}` | 200 summary | **requires `Idempotency-Key`** |
| POST `/projects/{id}/decisions/wage-determination` | `{by, note, determination, schedule, rows, employer_burden, production_rates_approved, certified_payroll_admin}` | 200 summary | **requires `Idempotency-Key`** |
| POST `/projects/{id}/decisions/crew-plan` | `{by, note, preferred_crew?, assignments?{task_id: crew_id}, use_default_for_unassigned, difficulty{default, overrides?}}` | 200 summary | **requires `Idempotency-Key`** |
| POST `/projects/{id}/crew-plan/preview` | `{preferred_crew?, assignments?, use_default_for_unassigned, difficulty}` | 200 `{draft:true, problems[], valid, estimate\|null, economics\|null, pricing_blocked_by[], comparison\|null}` | rate-limited, size-bounded, non-mutating |
| POST `/projects/{id}/release` | `{approver, expected_scope_version, expected_proposal_digest, note?}` | 200 `{proposal_digest, approved_by, released_at, scope_version, qualifications, audit_id, status}` | engine digest check |
| DELETE `/demo/projects/{id}` | none | 200 `{deleted:true}` | owner-checked |

Stable codes: `UNAUTHORIZED` 401; `NOT_FOUND` 404 (unknown project, wrong/missing owner: indistinguishable); `BAD_REQUEST` 400; `IDEMPOTENCY_KEY_REQUIRED` 400; `IDEMPOTENCY_KEY_REUSED` 409; `CREW_NOT_IN_FLEET` 409; `DECISION_UNCHANGED` 409 (crew plan, wage determination); `WAGE_MODIFICATION_NOT_HIGHER` 409; `WAGE_HISTORICALLY_CLEARED` 409; `WAGE_HISTORY_UNAVAILABLE` 409; `WAGE_MODIFICATION_STALE` 409; `WAGE_SUPERSESSION_REQUIRED` 409; `RULESET_ALREADY_APPROVED` 409; `ENGINE_REFUSED` 409 (+ `engine_codes[]` such as `CREW_UNSUITABLE`, `CREW_NOT_SELECTED`, `WAGE_*`, `CREW_PLAN_STALE`; text is the engine's); `TOO_MANY_ASSIGNMENTS` 400; `BODY_TOO_LARGE` 413; `PREVIEW_BODY_TOO_LARGE` 413; `PREVIEW_RATE_LIMITED` 429 (+ `Retry-After`, `retry_after_seconds`, `limit_scope`); `RATE_LIMITED` 429 (per-project mutation cap); `NOT_IMPLEMENTED` 501; `UNAVAILABLE` 503.

## 3. Engine versus workflow ownership
| Decision | Adapter calls | Owner |
|---|---|---|
| ruleset approval | `workflow.approve_quantity_ruleset` | workflow (no `pricing_service` v1 function) |
| wage determination | `pricing_service.record_wage_decision` | pricing_service wrapper over workflow |
| crew plan | `pricing_service.adopt_crew_plan` | pricing_service wrapper over workflow |
| release | `workflow.release` | workflow |
The adapter adds pre-checks (fleet, idempotency, bounds) and never alters engine state except through these calls.

## 4. Crew eligibility and fleet membership
Two independent checks. (a) **Fleet membership** (adapter, before the engine): preferred crew and every assignment must be in `pricing_service.fleet_overview(book).crews` (authoritative engine metadata; never a hard-coded list); `use_default_for_unassigned=true` is dry-run on a private copy and refused if any task would fall back to a non-fleet crew. Code `CREW_NOT_IN_FLEET`. (b) **Task qualification** (engine): required roles/qualifications, production rate, wage clearance; code `ENGINE_REFUSED` with `CREW_UNSUITABLE` (e.g. missing R4 for drilling). Fleet membership never grants eligibility and eligibility never grants fleet membership. Tests: `test_fleet_enforcement.py`.

## 5. Preview invariants (tested: `PreviewLimits`, `Fleet`)
Preview never changes project state, audit, plan version, approvals or digest; never counts against the mutation cap; never reaches release. It applies the same fleet rule as the decision. It returns the exact engine problems and, when valid and wages are cleared, an estimate/economics computed on a private deep copy.

## 6. Idempotency and audit semantics (tested: `Idempotency`)
`Idempotency-Key` (8-128 chars `A-Za-z0-9_.:-`) is **required** on the three decision routes; scope: per project. Same key + same canonical payload (route + whole JSON body, so `by` and `note` are part of the identity) -> the original stored response (since pass 4 stored and re-sent as the exact serialized bytes of the original response; verified by raw-byte tests, whereas pass-2/3 evidence compared only PARSED JSON), headers `Idempotent-Replay: true`, `X-Idempotency-Result: historical`, `X-Original-Audit-Event-Id`, **no engine event, no version, no mutation count**. **Ordering (pass 3):** the replay lookup runs after owner/session/project validation and *before* the mutation cap, so an exact replay of an accepted decision is served even at or beyond the cap; a changed payload or actor is NOT a replay and is capped normally (429 `RATE_LIMITED` at the cap, otherwise 409 `IDEMPOTENCY_KEY_REUSED`). **A stored response is the HISTORICAL result of the original decision, not current state and not current authorization**: after a newer decision it shows the old plan version and digest; clients must GET the project for current state, and release always checks the live digest (a replayed old digest is refused). Retention: last 200 keys per project, in memory. Same key + different payload or route -> 409 `IDEMPOTENCY_KEY_REUSED`. Only successful decisions are recorded; a refused attempt does not burn its key. A new key is an intentional new decision: identified in `summary.adapter.decisions[]` (`idempotency_key, route, payload_sha256, by, audit_event_id, recorded_utc, actor_identity`) and linked to the engine audit event; prior audit history and plan versions are never rewritten or reset. An identical crew plan under a new key is refused (`DECISION_UNCHANGED`) and a repeat approval of an already-approved ruleset digest is refused (`RULESET_ALREADY_APPROVED`) so approver attribution cannot be overwritten. The ledger is **in memory, per process** (section 12).
**Engine change requested for review (not implemented):** `workflow.approve_quantity_ruleset` and `approve_crew_plan` should themselves refuse an unchanged re-approval, and `proposal_digest` should not bind `approved_utc`/`note` of the crew plan; until then these guarantees live only in this adapter.

## 7. Wage, ruleset and production gates
Pricing requires, in order: Scope Gate clear; named ruleset approval of the exact digest; (prevailing-wage projects) a fully cleared wage determination; an approved crew plan; then release against the exact digest. `contractor_approved` is **hard-coded false** in the summary: a demo ruleset approval is a self-declared visitor action and never represents the owner's contractor approval, which is outstanding. Production policy refuses draft rules. `pricing_service` is unchanged.

### 7a. Wage-determination policy (pass 4; adapter pre-check, `pricing-service.v1` and workflow unchanged)
**Invariant:** a changed wage determination at the SAME statutory modification may be corrected only if it is currently uncleared AND server-side history shows it has NEVER been cleared or used to authorize pricing. That history is irreversible.
**Authoritative source of history:** the adapter's per-project **wage history** (`adapter.wage_history`): created by the adapter when the project is created (so complete from its first event), append-only, server-side, in the same lifetime as the project. One record per accepted wage decision `{seq, decision_id, modification, content_sha256, by, audit_event_id, ever_cleared, ever_authorized_pricing, first_cleared_audit_event_id}`. Flags are monotonic (False -> True only). They are set by an observation run at the start of every request for the project and after every mutation/release: current wage record cleared => `ever_cleared`; an estimate/digest exists on it => `ever_authorized_pricing`. Never from a client field (unknown fields are 400; flags inside `determination` are ignored text), never from current status alone, never from absence of history.
**Survives invalidation:** engine voiding (scope/labor change), expiry, plan changes, wage edits, rate-book changes and session transitions never touch the history; it is dropped only with the project. A history/engine mismatch marks the history permanently `complete=false`: a different decision id, modification or actor, **or (pass 5) different canonical wage CONTENT** (see 7b), or a missing/malformed committed content identity. Once untrusted, a project's wage history stays untrusted: only a strictly higher modification is accepted afterwards (it does not restore trust, earlier flags are never reset, and later same-or-lower-modification edits on any record of that project fail closed with `WAGE_HISTORY_UNAVAILABLE`).
**Missing or incomplete history fails closed:** every wage submission that is not strictly higher than the recorded modification is refused with `WAGE_HISTORY_UNAVAILABLE`.
| Situation | Result |
|---|---|
| same key, identical canonical request | original (historical) response, no event |
| same key, different request/actor/note | 409 `IDEMPOTENCY_KEY_REUSED` |
| different decision_id than the recorded one | 409 `WAGE_SUPERSESSION_REQUIRED` (no supersession action exists) |
| higher modification than the recorded one | recorded as a new, separately audited decision; history retained |
| lower modification than any ever recorded for the decision | 409 `WAGE_MODIFICATION_STALE` (also after the engine voided the record) |
| history missing/incomplete (not strictly higher) | 409 `WAGE_HISTORY_UNAVAILABLE` |
| same modification, identical content, record present | 409 `DECISION_UNCHANGED` (never recorded again, never re-attributed) |
| same modification, changed content, currently cleared | 409 `WAGE_MODIFICATION_NOT_HIGHER` |
| same modification, changed content, ever cleared or ever authorized pricing (even if uncleared now or voided) | 409 `WAGE_HISTORICALLY_CLEARED` |
| same modification, changed content, uncleared, never cleared, history complete | allowed: a correction; prior version stays in the audit log, history and ledger |
| same modification, identical content to the latest version, after the engine voided the record | allowed (re-verification) |
Rejected requests leave state, ledger, history, plan versions and digests unchanged. **Quota policy (unchanged):** a refused or malformed attempt that is not an exact replay counts toward the demo mutation cap; an exact replay never does.
**Residual limitation (honest):** the engine does not itself record clearance, so the history is an adapter observation. A clearance that began and ended with no request in between could be missed, but pricing authorization needs a request, and the observation also runs after it. **Smallest reviewed amendment proposed (not implemented):** have `workflow` append an engine-owned `wage_determination_cleared` audit event the first time a recorded determination derives a labor decision (and `wage_determination_superseded` on overwrite); the adapter would then read engine history instead of observing.

### 7b. Wage content identity `wage-content-identity-v2` (pass 5 spec v1; pass 6 v2 adds ambiguity rejection, see 7c)
Each history record commits `content_identity` = sha256 of canonical JSON (sorted keys, no whitespace, ASCII, no NaN) of: `determination{decision_id, modification (as text), date, valid_through, source_ref}`; `schedule[{classification, base_rate, fringe_rate}]` and `rows[{role_key, classification, classification_status, conformance_ref, base_rate, fringe_rate, source_ref}]` (lists order-independent, sorted by each element's own canonical JSON, duplicates preserved; unknown keys dropped exactly as the engine drops them); `employer_burden` (ALL keys, e.g. `pct`, `source_ref`); `production_rates_approved`; `certified_payroll_admin` (ALL keys). Numbers are exact decimals (24, 24.0 and 24.00 are equal; booleans are not numbers); NaN/inf or any non-JSON type is an error, never coerced. **Excluded:** `recorded_by`, `note`, `recorded_utc`, `scope_version`, `ratebook_labor_sha256` (observation/binding metadata managed by the engine), and all derived or display values (blockers, cleared, computed rates, estimate). Checks: (a) at every request and before any mutation the LIVE engine record's identity must equal the latest committed identity for its decision/modification/actor; (b) after the engine accepts a decision the committed identity is computed from the engine's LIVE record and must equal the identity of the request, else the history is untrusted; (c) a missing, malformed (not 64 lowercase hex), wrong-spec or uncomputable identity is a mismatch. Client-supplied digests/flags are unknown fields (400) or ignored text and never confer authority. Identity also defines 'unchanged' (`DECISION_UNCHANGED`): semantically identical content, however ordered or typed, is unchanged. Limitation: the live record is read from engine state because no engine function exposes it; an engine-provided content digest is a proposed amendment.

### 7c. Role-key uniqueness (pass 6)
**Root cause:** `pricing/prevailing.py` matches wage rows to roles by exact `role_key` and uses the FIRST row for a role (later rows are reported as unknown) and keys the schedule by `classification.strip().lower()` (last duplicate wins in its dict), while identity v1 sorted rows/schedule as an unordered set; two different R1 rows in a different order therefore shared one identity but evaluated differently. **Rule (derived from those semantics, no invented aliases):** (a) no two rows may share the same `role_key` string (exact equality; `R1`, `r1` and `R1 ` are three different keys, the last two being unknown roles the evaluator itself flags); (b) no two schedule entries may share the same `classification.strip().lower()` (non-string/blank classifications are not keys). Applies even when the duplicates have identical values. Violations are rejected **first**, before any history lookup, identity commitment or engine call, with HTTP 400 and stable codes `WAGE_ROW_DUPLICATE_ROLE` / `WAGE_SCHEDULE_DUPLICATE_CLASSIFICATION` (`details[{code,key}]`); nothing is merged, repaired or first/last-picked; state, audit, ledger, history, pricing, plan version and digest are unchanged; a rejected request is not stored for replay; the rejected-attempt quota policy is unchanged (+1, exact replays never count). Duplicate-bearing content has **no identity** (`WageAmbiguity`). Unique-key content is order independent for identity AND evaluator (asserted over all 48 row/schedule orderings). **Existing history:** a record committed under identity v1 stays trusted only if the live record is unambiguous and its v1 identity (recomputed under v1) still matches; a live record with duplicate keys is NOT trusted even if its old hash matches (history becomes permanently untrusted, same-or-lower-modification edits fail closed, the old record and identity are never rewritten or erased); a strictly higher modification and the monotonic `ever_cleared`/`ever_authorized_pricing` flags are unchanged. Scope note: duplicates can still be recorded by calling `workflow.record_wage_determination` directly (frozen, not changed); over HTTP there is no path around the adapter check. Engine-side rejection of duplicate rows is a proposed amendment.

## 8. Digests and invalidation
`proposal_digest` is issued only by the engine and binds scope, takeoff, estimate, labor decision, rate-book ref, quantities, ruleset hash/approver and the whole crew plan. Any new plan, wage modification, ruleset change, scope change or rate-book/profile change moves it; a stale digest or scope version is refused at release (409 `ENGINE_REFUSED`). Plan versions strictly increase and are never reused. An old digest never authorizes a changed plan (tested).

## 9. Demo actor identity restrictions
`by`/`approver` are free-text and **SELF-DECLARED, NOT AUTHENTICATED**; `X-Demo-Owner` is a client-chosen session id. Every summary states `adapter.actor_identity = SELF_DECLARED_DEMO_ACTOR_NOT_AUTHENTICATED`. No route may be treated as production authority. Production authentication, roles and separation of duties are NOT IMPLEMENTED.

## 10. Session isolation and rate limits
Missing/wrong `X-Engine-Key` 401; wrong/missing owner 404 (existence not revealed); keys, ledger and limiter state are per project/owner and dropped with the project. Limits: demo mutation cap 100 per project (refused attempts count; exact replays do not); preview 20/min per project and 60/min per owner (env `PREVIEW_MAX_PER_MINUTE`, `PREVIEW_MAX_PER_OWNER_PER_MINUTE`), preview body <= 8192 bytes, assignments <= number of labor tasks. **These limits live in one process's memory. They are a local-demo guard, NOT a shared/global public guarantee.** A public deployment must (i) run the engine on **private ingress only**, reachable solely through an enforced proxy (or equivalent boundary) that holds the engine key, authenticates visitors and enforces shared per-IP/per-session rate limits and body limits, and (ii) not rely on this limiter across workers/instances.

## 11. Output data classification
Allowed (FICTIONAL_DEMO book only): derived estimate values, matched line unit prices/vendors/price dates for lines actually priced, per-crew hourly cost, role names, `ratebook_ref{id,version,effective_date,content_sha256,labor_sha256}`. Never returned: the workbook, its file hash, role wage tables, unused rates, private store paths, credentials, other sessions' ids. Enforced by `test_api_disclosure.py` (reviewed key allowlist; new keys fail until reviewed) and `test_ratebook_containment.py`. A `COMPANY_PRIVATE` book is refused at project creation by policy; exposing matched prices for a private book would need a new classification decision.

## 12. Persistence and concurrency
Projects, ledger and limiter are in memory; a restart loses them. Requests serialize on one process-wide lock; there is no multi-instance consistency, no shared idempotency store and no durable audit. Not suitable for production use.

## 13. Units and rounding
Money USD, rounded half-up to cents per line (engine `_c`); totals are sums of rounded lines. Crew hours/worker hours/crew-days floats rounded to 6 dp; `crew_hourly_cost` 4 dp; percentages 1 dp half-up (`fleet_average_display`), exact value also given (`fleet_average_exact_pct` 95.75). Hours are effort; `calendar_duration` is null (no scheduling model).

## 14. Profitability labels (math unchanged; terminology awaiting the owner)
`gross_profit` = price - direct cost; `net_profit` = gross profit - overhead - contingency (equals the engine's profit line). Both are **estimated at bid**; contingency is a reserve priced into the bid and is deducted only for projection, not because it was spent; neither is realized profit (`economics.realized=false`, `labels`, `contingency_note`, `terminology_status = AWAITING_JORDAN_BUSINESS_APPROVAL`). The portfolio fixtures compute net profit as gross profit minus allocated overhead only (no contingency), a second, differently-scoped definition awaiting the same decision. LOOM verified there is no double deduction.
